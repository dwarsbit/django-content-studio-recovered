# 📑 List page

Every registered model gets a list page, where editors search, filter, sort
and act on its objects. You configure it on the model's studio, next to the
options on [Registering models](/docs/registering-models).

The list page shows objects as a **table**, the default, as a **list** of
readable items, on a [**calendar**](#calendar) by a date, on a
[**board**](#board) in columns by a choice or a relation, or as a
[**gallery**](#gallery) of images. Set the views
to offer with `list_views`; with more than one, editors switch with a
toggle and the admin remembers their choice per model.

<Screenshot name="articles" alt="The list page of articles, with search, filters and a table of titles, status, views, authors and dates" />

```python
# blog/admin.py
from content_studio import register
from content_studio.admin import ModelStudio

from .models import Article


@register(Article)
class ArticleStudio(ModelStudio):
    table_display = ["title", "status", "published_at"]
    list_views = ["table", "list"]
    list_item_display = {
        "title": "title",
        "description": "body",
        "meta": "get_status_display",
        "thumbnail": "cover",
    }
```

### Table columns

`table_display` lists the table's columns: field names, or `TableColumn`
objects for a custom header, a format or a computed value.

```python
# blog/admin.py
from content_studio import register
from content_studio.admin import ModelStudio
from content_studio.form import TableColumn
from content_studio.formats import NumberFormat

from .models import Article


@register(Article)
class ArticleStudio(ModelStudio):
    table_display = [
        "title",
        TableColumn(field="published_at", header="Published"),
        TableColumn(field="get_word_count", header="Words", format=NumberFormat),
    ]

    def get_word_count(self, obj, request):
        return len(obj.body.split())
```

A column's `field` is a model field or a method on the studio. A method
takes `(obj, request)` and returns a value its format can show: text for text
formats, a number for `NumberFormat`, an ISO 8601 string for the date and
time formats. Without a `format`, a method column shows text and a field
column uses its field type's format.

A column without a `header` uses the field's verbose name; a method column
without one has no header. Editors can only sort on columns backed by a model
field.

`list_display`, the classic Django admin's name for the table columns, also
works, so a studio ported from the classic Django admin keeps its columns.
System check `content_studio.W010` asks you to rename it to `table_display`;
when both are set, `table_display` applies.

### List items

`list_item_display` maps the parts of a list item to field or method names:
a prominent `title`, a muted `description`, a `meta` label on the right and a
`thumbnail` on the left.

The `thumbnail` is an image or file field, a media field or a method or
property that returns an image URL; in these examples, `cover` is an
`ImageField` on `Article`. A media field shows images only, using the site's
[small thumbnail](/docs/media-library#thumbnails). Once one item on the page has a thumbnail, items
without one show a placeholder, so the titles stay aligned.

For items computed in code, override `get_list_item_display` instead:

```python
# blog/admin.py
from content_studio import register
from content_studio.admin import ListItemDisplay, ModelStudio

from .models import Article


@register(Article)
class ArticleStudio(ModelStudio):
    list_views = ["table", "list"]

    def get_list_item_display(self, obj, request):
        return ListItemDisplay(
            title=obj.title,
            description=obj.author.get_full_name(),
            meta=obj.status,
            thumbnail=obj.cover.url if obj.cover else "",
        )
```

### Model properties

The admin shows a model's `@property` only where the studio names it: as a
column in `table_display`, a field in `edit_main` or `edit_sidebar`, or an
entry in `readonly_fields`. A property you do not name is never computed
and never sent to the admin, so a property that holds a secret or runs a
query stays out of every list page and edit page.

```python
# blog/admin.py
from content_studio import register
from content_studio.admin import ModelStudio

from .models import Article


@register(Article)
class ArticleStudio(ModelStudio):
    table_display = ["title", "word_count"]
```

Here `word_count` is a property on `Article`, shown as a table column. A
property named in `list_item_display` is computed for each item of the list
view.

## Editing in the table

`table_edit` names the table columns editors can change in place, without
opening the edit page:

```python
# blog/admin.py
from content_studio import register
from content_studio.admin import ModelStudio

from .models import Article


@register(Article)
class ArticleStudio(ModelStudio):
    table_display = ["title", "author", "featured", "views", "status"]
    table_edit = ["author", "featured", "views"]
```

The first column opens the object, so it is never edited in place, as in
the Django admin.

A cell saves as soon as the editor leaves it: Enter or a click elsewhere
saves a text or number cell, Tab saves it and moves on to the next editable
cell, and Esc puts the old value back. Switches, selects, dates and pickers
save when they change. A toast names the saved field and offers Undo. The
other cells of the row still open the edit page.

A cell edits these fields:

| Field | Cell |
| --- | --- |
| `CharField`, `TextField`, integer, decimal and float fields | Input |
| `BooleanField` | Switch |
| Any field with `choices` | Select |
| `DateField`, `DateTimeField`, `TimeField` | Date and time picker |
| `ForeignKey` | Search picker, like the edit page's |

A save goes through the same path as the edit page: the studio's
[save hooks](/docs/edit-page), the model's `clean()` and unique checks, the
editor stamps and the [history](/docs/history). An invalid value stays in the
cell with the reason, until the editor fixes it or presses Esc.

Each save sends the value the editor saw. When someone else changed that
field since the list loaded, the cell refuses the save and says so; Esc
then shows their value. Other fields of the row save as usual.

A cell is only editable for editors with change permission, and only for
fields the edit page writes: fields left out of `edit_main` and
`edit_sidebar` and read-only fields stay plain. Rows the editor may not
change (the object form of `has_change_permission`) stay plain too, with a
lock on hover.
On a [translated](/docs/translations) field, the cell edits the language
the list shows. Override `get_table_edit(request)` to choose the columns
per request.

`list_editable`, the classic Django admin's name, also works. System check
`content_studio.W032` asks you to rename it to `table_edit`, and warns
when `table_edit` is set on a studio without the table view.
`content_studio.E057` reports names that are not `table_display` columns
or fields the edit page writes, the first column, read-only fields, many-to-many and reverse
relations, fields with their own widget (rich text, blocks, media) and the
fields [publishing](/docs/publishing) sets, which the Status column and
the Publish actions change.


## Calendar

The calendar view shows the objects on a month grid by a date field, with
the list's search and filters. Add `"calendar"` to `list_views` for the
[publishing](/docs/publishing) date, so scheduled content shows on the day
it goes live:

```python
# blog/admin.py
from content_studio import register
from content_studio.admin import ModelStudio

from .models import Article


@register(Article)
class ArticleStudio(ModelStudio):
    publishing = "published_at"
    list_views = ["table", "list", "calendar"]
```

For another date, name the field with `CalendarView`:

```python
# events/admin.py
from content_studio import register
from content_studio.admin import ModelStudio
from content_studio.list_views import CalendarView

from .models import Event


@register(Event)
class EventStudio(ModelStudio):
    list_views = [
        "table",
        CalendarView("starts_on", end="ends_on", label="Programme"),
    ]
```

| Option | Default | Description |
| --- | --- | --- |
| `field` | the publishing date | A `DateField` or `DateTimeField` of the model. |
| `end` | `None` | An end date field: the object shows on every day from its date through its end. |
| `label` | the field's name | The view's name in the view switch. |
| `editable` | `True` | Whether editors may drag items to another day. |

Each item shows its time and its [list item](#list-items) title; with
publishing, a dot gives its state (draft, scheduled, published, expired).
A day with more than three items shows "+N more", which opens the whole
day. One range shows up to 500 items and says so when there are more;
search and filters narrow it. Items without a date wait in the **No date**
tray beside the grid, when the field may be empty. On a phone the month
becomes a list of the days that have items.

Dragging an item to another day saves its new date at once, keeps its
time, and offers Undo in a toast:

- On the publishing date it **reschedules**: scheduled and draft items
  move to a future day (a draft dropped on a day is scheduled), and
  dropping one on the tray makes it a draft again. Published and expired
  items stay where they are. Editors need the model's Can publish
  permission.
- On another date it saves the field (and moves the end along) through
  the same path as [editing in the table](#editing-in-the-table): change
  permission, the studio's save hooks, the model's `clean()`, the
  history, and a refusal when someone else changed the date since the
  calendar loaded. Rows the editor may not change stay put.

Set `editable=False` to show the calendar without dragging. Each calendar
of a studio needs its own field; offer two calendars by naming two
fields. `content_studio.E059` reports `"calendar"` on a studio without
publishing, and `content_studio.E060` a calendar field that is not a date
field or one that two calendars share.

## Board

The board view shows the objects as cards in columns, one per value of a
field with choices or a foreign key, with the list's search, filters and
ordering. Dragging a card to another column changes the value:

```python
# blog/admin.py
from content_studio import register
from content_studio.admin import ModelStudio
from content_studio.list_views import BoardView

from .models import Article


@register(Article)
class ArticleStudio(ModelStudio):
    list_views = ["table", "list", BoardView("stage")]
    edit_sidebar = ["stage", "author"]
```

| Option | Default | Description |
| --- | --- | --- |
| `field` | | A field with `choices`, or a `ForeignKey`. |
| `columns` | every choice | The values to show as columns, in order. For a foreign key, primary keys; by default its first 12 objects. |
| `label` | the field's name | The view's name in the view switch. |
| `editable` | `True` | Whether editors may drag cards to another column. |

A card shows the [list item](#list-items) thumbnail, title, description
and meta, or the publishing state. Each column shows its count and first
20 cards, with **Show more** below. Items without a value get a leading
"No *field*" column when the field may be empty. A foreign key's columns
are the objects its picker offers the editor. With bulk actions, cards
get a checkbox for the bulk bar; with row actions, a menu. The **+** of a
column creates an object with that value, for editors who may add.

Dragging a card saves the new value at once through the same path as
[editing in the table](#editing-in-the-table): change permission, the
studio's save hooks, the model's `clean()`, the history, and a refusal
when someone else changed the value since the board loaded. A toast
offers Undo. The field must be on the edit page and not read-only; rows
the editor may not change stay put. Set `editable=False` to show the board
without dragging.

`content_studio.E061` reports a board field without choices that is not a
foreign key, columns that are not choices of the field, and two boards of
one field.

## Gallery

The gallery view shows the list as image tiles: the
[list item](#list-items) thumbnail with the title under it. Add
`"gallery"` to `list_views` and map the `thumbnail` role:

```python
# blog/admin.py
from content_studio import register
from content_studio.admin import ModelStudio

from .models import Article


@register(Article)
class ArticleStudio(ModelStudio):
    list_views = ["table", "list", "gallery"]
    list_item_display = {
        "title": "title",
        "meta": "get_status_display",
        "thumbnail": "cover",
    }
```

The thumbnail can be an image or file field, a media library item (its
small thumbnail) or a method returning a URL. Items without one show a
placeholder. With publishing, drafts, scheduled and expired items carry
their state on the image; otherwise the large tiles show the meta badge.
The gallery pages, searches, filters and sorts like the list. Editors
switch between large and small tiles in the toolbar, remembered per
model. With bulk actions, a tile gets a checkbox on hover; with row
actions, a menu. On a phone the gallery has two columns.

`content_studio.W033` warns about a gallery without a `thumbnail` role,
unless the studio computes its items with `get_list_item_display`.

## Filters

`list_filter` lists the filters above the list. Each entry is a field
name, a path across relations, or a filter class of your own.

```python
# blog/admin.py
from content_studio import register
from content_studio.admin import ModelStudio

from .models import Article


@register(Article)
class ArticleStudio(ModelStudio):
    list_filter = ["status", "published_at", "author", "author__country"]
```

Each field gets the control that fits it:

- a choice list for fields with choices;
- Yes and No for booleans;
- a date range for dates;
- a minimum and maximum for numbers;
- a searchable picker for foreign keys and many-to-many fields;
- for text without choices (a `CharField`, `TextField`, `SlugField`,
  `EmailField` or `URLField`), a searchable list of the values in the
  table, like the classic admin's `AllValuesFieldListFilter`. It shows the
  first 100 values; searching finds the others. Editors can pick several.

Fields the list page cannot filter on, such as JSON, file and media
fields, are left out. `manage.py check` warns about them as
`content_studio.W034`; filter on them with a [custom filter](#custom-filters).

### Filters across relations

A path such as `"author__country"` filters on a field of a related model,
like the classic admin. It works across foreign keys, many-to-many fields
and reverse relations. The filter's label joins the verbose names, here
"Author country", and its control fits the last field.

Only the paths in `list_filter` filter, with the lookups their last field
has. A filter on `"author"` does not let editors filter on other fields of
the author. Content Studio also refuses paths that would expose what the
admin hides:

- the user model's password;
- fields that the model's studio leaves out with `exclude`.

`manage.py check` reports such paths as `content_studio.E042`.

### Custom filters

A filter class shows a list of options and decides itself what each option
matches. Subclass `ListFilter` and add the class to `list_filter`:

```python
# blog/admin.py
from content_studio import register
from content_studio.admin import ModelStudio
from content_studio.filters import ListFilter

from .models import Article


class PopularityFilter(ListFilter):
    title = "Popularity"
    parameter_name = "popularity"
    options = [("low", "Under 100 views"), ("high", "100 views or more")]

    def queryset(self, request, queryset, value):
        if value == "low":
            return queryset.filter(views__lt=100)
        return queryset.filter(views__gte=100)


@register(Article)
class ArticleStudio(ModelStudio):
    list_filter = ["status", PopularityFilter]
```

| Attribute or method | What it does |
|---------------------|--------------|
| `title` | The filter's label on the list page. |
| `parameter_name` | The name of the filter in the list's address. It must differ from the fields in `list_filter`. |
| `options` | The options, as `(value, label)` pairs. |
| `get_options(request)` | Override it to build the options when the filter opens, for example from the database or for the signed-in user. Returns `options` by default. |
| `multiple` | `True` lets editors pick several options. `queryset` then receives a list of values. |
| `queryset(request, queryset, value)` | Returns the filtered queryset. Returning `None` leaves the list unfiltered. |

Inside the filter, `self.studio` is the model's studio. The admin only
passes values that are among the options, so `queryset` never has to deal
with unknown values. Option values may contain commas.

The options can come from the database. This filter offers the tags in
use and lets editors pick several:

```python
class TagFilter(ListFilter):
    title = "Tag"
    parameter_name = "tag"
    multiple = True

    def get_options(self, request):
        return Tag.objects.values_list("slug", "name")

    def queryset(self, request, queryset, value):
        return queryset.filter(tags__slug__in=value)
```

Filters you wrote for the classic Django admin with `SimpleListFilter` work
in `list_filter` unchanged. Their `lookups()` are the options and
`queryset()` reads the value from `self.value()`, so they are single
choice. The `model_admin` they receive is the studio.

A `(field, FieldListFilter)` tuple from the classic admin filters on the
field with its default control. The filter class is ignored and
`manage.py check` warns about it (`content_studio.W005`).

## Bulk actions

In the table view, editors select objects (the header checkbox selects the
whole page) and run an action from the bar that appears. A selection belongs
to one page: paging, filtering or sorting clears it.

The built-in delete action is available to editors with delete permission.
Add your own actions to the studio with `@bulk_action`; like the actions of
the classic Django admin, they receive the request and the selected objects
as a queryset:

```python
# blog/admin.py
from content_studio import register
from content_studio.actions import bulk_action
from content_studio.admin import ModelStudio

from .models import Article


@register(Article)
class ArticleStudio(ModelStudio):
    @bulk_action(
        label="Publish",
        icon="ph-bold ph-paper-plane-tilt",
        confirm="Publish the selected articles?",
        allowed_permissions=["change"],
    )
    def publish(self, request, queryset):
        count = queryset.update(status=Article.Status.PUBLISHED)
        return f"Published {count} articles."
```

- `label`: the action's name; by default, the method name.
- `icon`: an icon class, like the studio's `icon`.
- `confirm`: a question to confirm before the action runs.
- `allowed_permissions`: the model permissions that allow the action; any one
  of them is enough. By default the action needs change permission. An
  empty list, `[]`, lets everyone who can see the list run the action. The
  permissions are also checked on each selected object (for example
  `has_change_permission(request, obj)`; with an empty list,
  `has_view_permission(request, obj)`): if any selected object fails, the
  action runs on none of them.

The return value is the message editors see: a number reports how many
objects changed, a string is shown as it is.

The built-in actions record every object they change in its history. Your
own actions record nothing by themselves. To record a change, call
`record_change` for each object, with `"created"`, `"updated"`,
`"deleted"`, `"restored"` or `"reordered"` and an optional message. Record a
deletion before you delete the object:

```python
# blog/admin.py
from content_studio import register
from content_studio.actions import bulk_action
from content_studio.admin import ModelStudio
from content_studio.signals import record_change

from .models import Article


@register(Article)
class ArticleStudio(ModelStudio):
    @bulk_action(label="Publish", allowed_permissions=["change"])
    def publish(self, request, queryset):
        articles = list(queryset)
        queryset.update(status=Article.Status.PUBLISHED)

        for article in articles:
            record_change(request, article, "updated", "Published.")

        return len(articles)
```

The studio's `actions` attribute chooses which actions are offered:

```python
actions = None                   # the default: delete, export and every @bulk_action
actions = []                     # no bulk actions
actions = ["publish", "delete"]  # exactly these, in this order
```

`"export"` names the built-in export, which is offered when the studio
[exports its list](#exporting-the-list).

System check `content_studio.E007` reports unknown or duplicate names and
an action that would replace the built-in delete or export.

### Asking for values first

An action can ask editors for values before it runs: "assign to...", "set
status to...". List them in `fields`, and the action opens a dialog with
those fields; the method then also receives the values, as a dictionary:

```python
# blog/admin.py
from django import forms
from django.db.models import Q

from content_studio import register
from content_studio.actions import bulk_action
from content_studio.admin import ModelStudio
from content_studio.form import Field

from .models import Article


@register(Article)
class ArticleStudio(ModelStudio):
    @bulk_action(
        label="Assign",
        icon="ph-bold ph-user-switch",
        fields=[
            # A model field: the edit page's widget and validation.
            "author",
            # Anything else: a Django form field.
            Field(
                "note",
                form_field=forms.CharField(required=False, widget=forms.Textarea),
            ),
            Field(
                "notify",
                form_field=forms.BooleanField(
                    label="Email the note to the author", required=False
                ),
                # Shown once a note is written.
                when=~Q(note=""),
            ),
        ],
    )
    def assign(self, request, queryset, data):
        count = queryset.update(author=data["author"])
        return f"Assigned {count} articles to {data['author']}."
```

- A field name refers to a model field. It looks and validates like on the
  edit page: its label, help text, choices, widget, and the related objects
  editors may pick. It is required unless the model field has `blank=True`.
- `Field(name, form_field=...)` adds an input that is not on the model,
  validated by the Django form field. Its `label`, `help_text`, `required`,
  `initial` and `choices` are used; `ModelChoiceField` and
  `ModelMultipleChoiceField` get the related object pickers, offering only
  the objects editors may see. `widget=` picks another
  [widget](/docs/widgets), as on the edit page.
- `when=` shows a field only when the dialog's values meet a condition, like
  [conditional fields](/docs/edit-page#conditional-fields) on the edit page
  (`Q` objects only). A hidden field is left out of `data`.

The values are validated on the server before the action runs; errors show
under the fields and the action does not run. In `data`, related objects
are model instances and dates are `date` and `datetime` objects. A
`ValidationError` the method raises shows in the dialog too. The `confirm`
text, when set, becomes the dialog's description.

System check `content_studio.E051` reports fields that are not model fields
and have no `form_field`, fields that cannot be edited, conditions that read
other fields or use a `Condition`, and a method without the `data` argument.

## Row actions

Each row of the list has a ⋯ menu with actions on that one object. By
default it offers Delete, and Duplicate when the studio
[allows duplication](/docs/edit-page). The studio's `row_actions` attribute
chooses them, by the same names as `actions`:

```python
row_actions = None                                       # the default: duplicate and delete
row_actions = []                                         # no row menu
row_actions = ["publish", "assign", "duplicate", "delete"]  # exactly these, in this order
```

`"duplicate"` and `"delete"` name the built-ins; other names are
`@bulk_action` methods, which run on the row's object with the same
permission checks, confirmation and [dialog](#asking-for-values-first) as in
the bulk bar. A row action does not need to be in `actions`. When the list
can be [reordered](#reordering), the moves join the same menu.

System check `content_studio.E007` reports unknown or duplicate names.

## Soft delete and the trash

By default, deleting an object removes it from the database. To move
objects to a trash instead, set `soft_delete` to a nullable date or date and
time field on the model that marks an object as trashed:

```python
# blog/admin.py
from content_studio import register
from content_studio.admin import ModelStudio

from .models import Article


@register(Article)
class ArticleStudio(ModelStudio):
    soft_delete = "removed_at"
```

With the option set:

- deleting fills in the field instead of removing the object, and the object
  disappears from the list page;
- the list page links to the model's trash, where editors restore objects
  (with change permission) or delete them for good (with delete permission);
- restoring an object is recorded in its history.

Any model with such a field works; the built-in `SoftDeletableModel` has one
called `removed_at`. System check `content_studio.E008` reports a field that
is missing or of the wrong type.

## Reordering

To let editors put objects in their own order, add a number field to the
model and name it in `reorder_field`. The list page then follows that
order, and every row gets a handle to drag it to another position:

```python
# blog/models.py
from django.db import models


class Category(models.Model):
    name = models.CharField(max_length=50)
    position = models.PositiveIntegerField(default=0)

    def __str__(self):
        return self.name
```

```python
# blog/admin.py
from content_studio import register
from content_studio.admin import ModelStudio

from .models import Category


@register(Category)
class CategoryStudio(ModelStudio):
    table_display = ["name"]
    reorder_field = "position"
```

With the option set:

- the table view and the list view show a drag handle on every row; editors
  drag rows with the pointer, or focus the handle and move the row with the
  keyboard (space to pick it up, the arrow keys to move it, space to drop
  it);
- each row's menu moves the object one step up or down, or to the top or
  the bottom of the list, also when that is on another page. A step up or
  down passes the neighboring object of the list as currently filtered;
- reordering needs change permission, and every move is recorded in the
  object's history;
- reordering is off while editors sort by a column or search, because then
  the list does not show the manual order. Filtering keeps it on.

A move does not call the model's `save()` method or send its signals. When
you add the field to existing rows, they can all start at `0`: the first
move numbers the list. If you set `ordering` yourself, start it with the
reorder field; system check `content_studio.W013` warns when it does not.

### Reordering per group

When objects are ordered within a group, such as reviews per article, list
the fields that form the group in `reorder_scope`. Objects then move among
the objects that share those values:

```python
# blog/admin.py
from content_studio import register
from content_studio.admin import ModelStudio

from .models import Review


@register(Review)
class ReviewStudio(ModelStudio):
    table_display = ["text", "article"]
    list_filter = ["article"]
    reorder_field = "position"
    reorder_scope = ["article"]
```

Filter the list by the group to see one order at a time. Inlines are always
ordered per parent, so an inline needs only `reorder_field`:

```python
# blog/admin.py
from content_studio.admin import InlineModelStudio

from .models import Review


class ReviewInline(InlineModelStudio):
    model = Review
    table_display = ["text", "stars"]
    reorder_field = "position"
```

On a model with a tenant field, objects are ordered per tenant (see
[Multi-tenancy](/docs/multi-tenancy)).

### Your own ordering

The built-in reordering works with a number field. If your model keeps its
order some other way, such as with django-ordered-model, override
`reorder` on the studio. It receives the object and either `after` or
`before`: the object to place it next to. Name the field the list is sorted
by in `reorder_field`:

```python
# blog/admin.py
from content_studio import register
from content_studio.admin import ModelStudio

from .models import Category


@register(Category)
class CategoryStudio(ModelStudio):
    reorder_field = "order"

    def reorder(self, request, obj, *, after=None, before=None):
        if after is not None:
            obj.below(after)
        else:
            obj.above(before)
```

Return `False` from `reorder` when nothing moved, so no change is recorded.

The built-in `ManualOrderModel` has an `order_key` field to use as the
reorder field, and its `reorder()` method numbers the order keys from `1`
again. Set `order_scope` on the model to the fields that form a group, like
`reorder_scope`.

System check `content_studio.E017` reports a reorder field that is missing
or, without your own `reorder`, not a number field, and `reorder_scope`
entries that are not model fields.

## Exporting the list

To let editors download the list as a spreadsheet, list the columns to
export in `export_fields`. Like `table_display`, it takes field names,
`__str__`, methods on the studio and `TableColumn` objects for a custom
header:

```python
# blog/admin.py
from content_studio import register
from content_studio.admin import ModelStudio
from content_studio.form import TableColumn

from .models import Article


@register(Article)
class ArticleStudio(ModelStudio):
    table_display = ["title", "status", "published_at"]
    list_filter = ["status"]
    search_fields = ["title"]
    export_fields = [
        "title",
        "status",
        "author",
        "published_at",
        TableColumn(field="word_count", header="Words"),
    ]

    def word_count(self, obj, request):
        return len(obj.body.split())
```

To export the table's columns instead, set `allow_export = True` and leave
`export_fields` out.

The list page then offers Export in the ⋯ menu next to Create. It downloads every object
that matches the current search and filters, on all pages, in the list's
current order. In the trash, Export downloads the objects in the trash. The
built-in Export bulk action, next to Delete, downloads only the selected
objects.

Exports are CSV files. To offer Excel files (`.xlsx`) as well, install
Content Studio with the `excel` extra, which adds
[openpyxl](https://openpyxl.readthedocs.io/):

```bash
pip install "django-content-studio[excel]"
```

Each column's header is the field's verbose name, capitalized, or the
`TableColumn` header. The cells hold the values as the admin shows them:

- the label of a choice, such as `Published`;
- the name of a related object, and the names of many-to-many objects
  separated by commas;
- dates and times in ISO format, such as `2026-04-01T18:30:00+02:00`, in
  the current time zone;
- `Yes` or `No` for booleans, and rich text without its markup.

In Excel files, numbers and dates are real numbers and dates, shown in ISO
format.

Exporting needs view permission on the model. An export holds the objects
of the selected tenant only, with [multi-tenancy](/docs/multi-tenancy), and
leaves out objects in the trash (except when exporting the trash) and the
fields in the studio's `exclude`. A value that a spreadsheet application
would read as a formula, because it starts with `=`, `+`, `-` or `@`, gets a
leading apostrophe so it stays text. Export is not available for
singletons.

To offer export in the ⋯ menu only, leave `"export"` out of an explicit
[`actions`](#bulk-actions) list.

System check `content_studio.E022` reports `export_fields` entries that do
not resolve, and `content_studio.W015` options that have no effect.

## Importing from a file

To let editors create and update objects from a file, set
`allow_import = True`, or list the fields a file may set in
`import_fields`:

```python
# blog/admin.py
from content_studio import register
from content_studio.admin import ModelStudio

from .models import Article


@register(Article)
class ArticleStudio(ModelStudio):
    table_display = ["title", "status", "published_at"]
    import_fields = ["title", "slug", "body", "status", "author", "published_at"]
    import_lookups = {"author": "username"}
```

`allow_import` takes the fields the edit page writes. Either way, an import
only sets fields the edit page writes: read-only fields, the tenant, file
fields and write-only password fields are never imported.

The list page then offers Import from file in the ⋯ menu next to Create.
Editors pick a CSV, Excel
(`.xlsx`) or JSON file, and the admin checks it first: it shows how many
objects the file creates, updates and leaves unchanged, and lists the
failing rows with their errors. Nothing is saved yet. When all rows are
valid, editors import them. When some fail, they fix the file and pick it
again, or import only the valid rows.

### Matching rows

A row with an `id` updates that object, and a row without one creates a
new object. An `id` that matches no object fails. To match rows on other
fields, such as a unique slug, name them in `import_id_fields`. A row that
matches an object updates it, and a row that matches none creates one:

```python
import_fields = ["title", "slug", "body", "status"]
import_id_fields = ["slug"]
```

`import_id_fields` should be unique together: a row that matches more than
one object fails. Updates set only the columns in the file, so a file with
an `id` and a `status` column changes the status and leaves the rest.

### Values

A file holds field names as headers (verbose names work too), then one row
per object. An import reads:

- a choice's value or its label, such as `published` or `Published`;
- `true`/`false`, `yes`/`no` or `1`/`0` for booleans;
- dates and times in ISO format, such as `2026-04-01T18:30:00+02:00`
  (without an offset, in the current time zone);
- the primary key of a related object, or the field `import_lookups` names
  for that relation, such as the author's username;
- many-to-many values and tags separated by commas, or as a JSON list;
- JSON for JSON fields.

Empty cells clear a value. Columns the import does not set, such as a
computed column of an export, are left out and the check says which.

The ⋯ menu also offers Export for import next to the regular export: a
CSV, Excel or JSON file with the values as an import reads them back, for
the current search and filters. Editors change it and import it again. The
import dialog also offers a template: the header row only. Excel files need
the `excel` extra, as for export.

### Permissions and history

Importing needs add or change permission on the model. Creating a row needs
add permission, and updating one needs change permission on that object.
Each row goes through the edit page's rules: the studio's
[save hooks](/docs/edit-page), the model's validation and, with
[multi-tenancy](/docs/multi-tenancy), the selected tenant. Objects in the
trash are never matched. Every created or changed object is logged in the
activity log, and with the history app it gets a version, as when an editor
saves it.

The check runs the save hooks inside a transaction that is rolled back.
Send emails and other work outside the database from
`transaction.on_commit`, so a check does not trigger them.

### Large files

An import runs in the request. Files with more than
[`IMPORT_MAX_ROWS`](/docs/settings#import_max_rows) rows (10,000 by
default) are refused. When your project's
[Django tasks](https://docs.djangoproject.com/en/stable/topics/tasks/)
backend runs tasks in the background, files with at least
[`IMPORT_TASK_ROWS`](/docs/settings#import_task_rows) rows (1,000 by
default) run as a task instead, up to
[`IMPORT_FILE_MAX_ROWS`](/docs/settings#import_file_max_rows) rows
(100,000 by default). Files over
[`IMPORT_MAX_SIZE`](/docs/settings#import_max_size) (10 MB by default) or
with more than 1,000 columns are refused, and reading a file stops at the
first row too many, so a large file is never parsed whole. The dialog then
shows the check's progress, and a notice follows the import itself. The
file and the job's progress wait in
[`UPLOAD_FOLDER`](/docs/settings#upload_folder) in
[`UPLOAD_STORAGE`](/docs/settings#upload_storage), so the storage must be
shared with the task workers. Closing the dialog after the check removes
the file; `content_studio_clear_uploads` removes what is left after a day. On the [system status](/docs/system-status#tasks) page, when
a task adapter lists your backend's tasks, the task is named "Import from
a file".

System check `content_studio.E048` reports import options that do not
resolve, and `content_studio.W026` options that have no effect or keys that
need not be unique.

## Large tables

The list page counts its objects to show the total and number the pages.
On tables with millions of rows that count is slow: an exact count reads
every row. Set `list_count` to show an estimate or skip the count:

```python
class OrderStudio(ModelStudio):
    list_count = "estimated"
```

| Value | The list page shows |
|-------|---------------------|
| `"exact"` | The exact number of objects and numbered pages (the default) |
| `"estimated"` | "About 2.3M orders" and previous and next buttons, once the table holds more than about 100,000 objects |
| `"none"` | No total, only "Page 3" and previous and next buttons |

With `"estimated"`, the estimate comes from PostgreSQL's query planner. It
covers the objects the editor can see, so the current tenant, the trash and
your `get_queryset()` are taken into account. Its accuracy depends on the
table's statistics, which PostgreSQL updates as it analyzes the table.
Below about 100,000 objects the list is counted exactly, since that count
is fast. A search or a filter is always counted exactly, because an
estimate of a filtered list can be far off. On other databases, such as
SQLite and MySQL, `"estimated"` counts exactly; use `"none"` there to skip
the count.

With `"none"`, a search or a filter shows no total either. Neither setting
counts the last page: there, the list shows the exact total it knows from
the rows on that page.

Pages without an exact total have previous and next buttons instead of
numbered pages, because a far page such as page 50,000 is slow to fetch and
an estimate can point past the real last page. The trash, inlines and the
media library are always counted exactly.

When an exact count of a list without a search or filter takes longer than
half a second, Content Studio logs a warning on the `content_studio`
logger, once per studio and process, that names the studio to set
`list_count` on. While `DEBUG` is on, the hint shows in the
[developer tools](/docs/developer-tools), with the code to copy.

System check `content_studio.E046` reports an unknown `list_count` value.
